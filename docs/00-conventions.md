# 0 How this project keeps its models in the record

This project is a trial of the [traceable-design](https://github.com/traceable-design/traceable-design) standard on a design that leans on simulation.
The standard has no record kind for a computational model, a tool, or a simulation run, so this page says how the project maps them onto what the standard has, and lists the gaps it found for feeding back.

## Mapping

| Thing | Where it lives | How the record sees it |
|------|----------------|------------------------|
| Model code (`sim/seawind.py`, `sim/aircraft.py`, `sim/dsearch.py`, `sim/structure.py`) | `sim/`, versioned by the git commit | A tool; never a fact. Its constants are values with status assumed (basis an open item) or sourced. |
| A number a model produces for a decision | `record/values.yaml` | Status calculated, basis the docs section that states the inputs and the model, or the check that verified it. |
| The model itself as a claim | `record/checks.yaml` | A new model is a T2 claim: a separate checker, told to refute it, hand-calculates or runs an independent model on a brief, and the result is a check with method refute, independent_model, or hand_calc. |
| A simulation run during design | the docs section that cites it | Not a Run (RN-nnn is for the physical thing). The section states the model version (commit), the inputs by key, and the outputs by key. |
| Generated files (`sim/viewer/field.js`, `sim/viewer/traj.js`) | `sim/viewer/` | Outputs of a script, committed so the viewer works from a checkout; regenerated by the commands in `docs/02-form.md#viewer`. They are not facts. |
| A measured value that later tests a prediction | `record/runs/` | Measured, citing its run; the comparison with the prediction goes back to the step that owns the model (S-17). |

## Gaps found, to report to the standard

Each gap is an open item of kind finding that waits for the owner as keeper of the standard (Q-030 to Q-044).
They name the ids of the standard that they concern (S, N, E) and no requirement of this project.
A section id in a basis is written as `docs/<file>.md#id`, and the heading ends in `{#id}`.

- Q-030: A model or tool has no record kind, id or version field; a shareable model has no schema; conventions have no place.
- Q-031: A design-time simulation run has no record kind; keyed values are copied as literals; calculated values are not rechecked.
- Q-032: The anchor of a `docs/<file>.md#section` basis is not verified, and the standard has no section-id syntax.
- Q-033: What makes a model the same (T1) or new (T2) is not stated, and E11 ignores the target and result of a check.
- Q-034: Generated files outside the tables have no staleness check, and the tool has no command to write the tables.
- Q-035: The standard has no stated mechanism for a project to report gaps (S-21 is a draft).
- Q-036: The design to build gate passes with no hazards and no parts.
- Q-037: A partial check cannot be superseded, and defects found by checks have no follow-up item.
- Q-038: A check names its author by role and carries no version.
- Q-039: Value keys inside a design point are not references.
- Q-040: A value cannot point to what it superseded, and has no withdrawn status.
- Q-041: An open item cannot wait on another item.
- Q-042: The decision trailer and the supersedes field take a single id.
- Q-043: The standard lists no allowed units.
- Q-044: The template root commit has no tier.

The owner decides whether to file them as issues on traceable-design/traceable-design.
